## 5. How much weight these deltas carry

**There is exactly one run per cell.** No seed repeats were trained for the dense runs, so no delta here has a standard error, and none of the project's usual significance machinery (paired SE, significant_2xSE, Welch — see `analysis/build_pooled_tables.py`) can be applied.

The only noise estimate the data can supply is the within-run spread of AP_S over the last 3 evaluation epochs of each run:

| run | AP_S at the last evals | spread |
|---|---|---|
| det_vitb_baseline_s1 | 17.861, 18.154, 18.460 | 0.599 |
| det_vitb_registers_s1 | 17.632, 18.159, 18.391 | 0.759 |
| det_vitb_saga_s1 | 17.472, 17.866, 17.616 | 0.394 |

The AP_S delta the verdict turns on (-0.844) is of the same order as that within-run spread (largest: 0.759). This is a statement about the precision of a single run, not a seed-level error bar, which would require repeats that do not exist.

## 6. Provenance and caveats

- **The registers rows are not backbone-matched.** They use `legacy_e2_vitb_registers_nomixdir` (`backbone_source: fallback`), the UNSEEDED legacy ViT-B registers checkpoint, because the seeded e2r registers run had not finished at launch. baseline and saga both use their seeded e2r s1 backbones. registers-vs-baseline deltas therefore mix a backbone change with a variant change.
- The segmentation registers run's best val mIoU is at epoch 29 while baseline and saga peak at 79; its val mIoU declined over the remaining epochs. Val-selection is working as designed, but the three columns are not read at the same point in training.
- Every table value is file-sourced; a run whose recorded backbone sha256 does not match the matrix candidate it names yields MISSING rather than a number from an unverified checkpoint.
